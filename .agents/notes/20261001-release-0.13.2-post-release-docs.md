## 发布路径

- 工作分支 `chore/release-notes-0.13.2`，改动提交 `b1f9290`（`chore(release): 0.13.2 release tags`，3 files changed）→ `--no-ff` 合并 `d03c3a5`（`Merge branch 'chore/release-notes-0.13.2'`）。
- 发布提交只改三个文件：
  - `README.md`：Herdr 安装 tag `--ref v0.12.1` → `--ref v0.13.2`；
  - `packages/herdsman-herdr-plugin/README.md`：同上；
  - `CHANGELOG.md`：0.13.2 段的状态行由 `**未发布**` 改为 `**已发布**`（新增写法，见下方"偏差记录"），并把"版本与引用同步"一行的"两个 README 的 Herdr 安装 tag 保持指向 `v0.12.1`（tag 尚未创建）"改写为"随发布提交同步至本版本创建的 `v0.13.2`"。
- 四个 manifest 的版本递增已在前一个提交 `e607fe2`（`chore(release): 0.13.2`）完成，不在本次发布提交里；这也是"发布提交的暂存文件 = 四个 manifest + 两个 README + `CHANGELOG.md`"这句话容易被读漏的地方——四个 manifest 只是该清单的一部分，且通常已在更早的提交落地。

## 决策

1. **`docs/releasing.md` 的暂存清单补 `CHANGELOG.md`**，并明写"发布提交的暂存集合 = 四个 manifest + 两个 README + `CHANGELOG.md`"（位置：`## Commit and create a local tag` 的 `git add` 块与其后说明句）。理由：清单原本只有四个 manifest 与两个 README，而 `CHANGELOG.md` 的"版本与引用同步"行（以及可选的状态行）必然在发布提交里改动，漏加会让紧随其后的 `test -z "$(git status --porcelain)"` 必然失败并中断发布。
2. **`npm profile get` 门禁换成可执行且等价的组合**（位置：`## Preconditions`）。新的门禁链 = `npm whoami` 必须等于发布者 + 两包目标版本必须 `E404` + `gh auth status` 通过 + 本文档后段的 tarball 打包与隔离安装验证。理由：自动化 token 无权读账号资料，`npm profile get` 必然以 `E403` 退出，把它当成“未登录”会误杀一次本来能成功的发布。**账号姿态（邮箱验证状态、2FA 模式）不在自动化门禁的覆盖范围内**——本机没有任何命令能证明它；它第一次真正的检验是 `npm publish` 自身的 PUT（被拒时不产生任何 registry 变更，修好重试同一版本即可），**页面级人工确认尚未记录**，是待办的一次性动作，完成后由执行者把 who / when / saw-what 记入发布笔记；检查面为 `https://www.npmjs.com/settings/dorokuma/profile`。跳过 `npm profile get` 属**永久已知限制，不是每轮偏差**：在 `.agents/notes/` 的发布笔记里**记一次**即可（附 E403 原文），不必每次发布重复记录。
3. **tag 创建时点写成硬约束**（位置：同上小节）：tag 必须在**发布提交（含 README 安装 tag 与 CHANGELOG 发布段）已 push 到 `main` 之后**创建，并给出快照校验命令——`git rev-list -n 1 "$TAG"` 必须同时等于 `HEAD` 与 `origin/main`；两个 README 各一条必须显示 `--ref $TAG`；`git show "$TAG:package.json"` 必须带 `$VERSION`；`git show "$TAG:CHANGELOG.md"` 必须含本版标题与事实行。理由：先打 tag 会把仍指向旧 tag 的 README、旧版本号或缺失本版标题的 CHANGELOG **永久**封进 tag 快照（tag 不可移动，恢复流程也禁止移动远端 tag）。
4. **CHANGELOG 发布段的写法写成规范**（位置：新增 `## Update the CHANGELOG` 小节，位于 `## Update versions` 与 `## Validate source and package contents` 之间）：**默认不写状态行**（按 0.12.1 先例，只保留"版本与引用同步""范围"两行）；另一种可接受写法是**只写"写提交那一刻已成立"的事实**（例如范围与版本/引用同步），不写 registry 侧结果。明写"**registry 侧事实（`latest` 前进、包可见、tag 指向）属发布后事实，写进 GitHub Release 正文与 `.agents/notes/` 发布笔记，不进 CHANGELOG 的发布提交**"。`**未发布**` 只保留给尚未发布的版本段。理由：本文件在"提交已推、产物未发"的窗口里写 registry 结果，会与 registry 现状不符；而发布中止或换版本时还要多补一次纠正提交。同时在恢复流程"更新四个版本文件"那一步补"修正替换版本的 CHANGELOG 段"（替换 = 改该段，不是再写一段）。另按"0.13.2 段不追溯改写"加一行过渡说明：该段已封在 tag `v0.13.2` 与 GitHub Release 里，新规自下一个发布起生效。
5. **部分发布时的版本档位归属写成用户决策**（位置：`## Recover from a partial publication` 第 4 条）：文档只给**按最后一个完整发布计算的默认值**（`calculated default`），agent 不得自行拍定；档位判据**锚定"最后一个完整发布的版本"**（两包都发布成功的那一版），不锚定残缺的根包版本。判据为"该次部分发布**含破坏性变更**（用户可感知的公共 API / CLI 命令 / 行为移除）→ 取下一个未用 minor，否则 → 取下一个未用 patch"。理由同 0.13.0 的 minor 抉择：档位直接决定 caret 使用者是否被要求显式升级。
6. **恢复流程补 `dist-tag` 回退**（位置：同上第 2 条）：确认 Pi 包缺席之后、递增版本号之前，把两包 `latest` 指回 `<lastGood>`（`npm dist-tag add "@dorokuma/herdsman@<lastGood>" latest`，pi 包同款），用途是让"等用户拍版本档位"这段时间没有用户可见成本——替换版本 publish 成功后会自动把 `latest` 推上去，期间 `latest` 不会指向那半份残缺发布。
7. **恢复流程补"长期中止"分支**（位置：同上小节末，`Do not move a remote tag…` 之后）：若最终决定不换版本、不发布，则 `main` 上已推的发布提交里与事实不符的措辞**必须由一次纠偏提交**处理（不得改写已推历史）；**远端 tag 不得移动**——tag 若已推则保持不动，纠偏提交也不碰它。

4. **恢复流程的 tag 删除与硬约束的咬合（tag 的"创建"与"推送"是两个维度）**：本地可能已经 `git tag -a` 建好 tag，而远端还没 `git push`。恢复流程第 3 步 `git tag -d "$TAG"` 删的是**本地已创建、远端未推送**的 tag，与决策 3 的硬约束（tag 必须在发布提交已 push 到 `main` 之后再创建）不冲突：硬约束管的是"创建 vs push 发布提交"的先后，恢复删除管的是"未推送即可作废"。但若在发布提交 push **之前**就建了 tag，恢复时除删 tag 外还要同时回退 README / CHANGELOG，这正是决策 3 要避免的形态。
5. **`npm token list` 已实测：可用，但刻意不纳入自动化流程**。本机实测 `npm token list --json` **exit 0**，返回 1 个 token，字段含 `bypass_2fa: true`、`permissions: [{ name: "package", action: "write" }]`、`expiry: 2026-11-20T05:16:26.940Z`（`created: 2026-08-22`）——即这条命令**能读出账号/令牌资料**，并非不可用，所以"未实测"不再是理由。**不纳入自动化发布流程的真实理由是：它会把 token 元数据（令牌标识、权限、到期时间）写进发布日志**，与"凭据不扩散"相抵。因此文档不复用它替代门禁，账号姿态改按"账号级一次性检查（`https://www.npmjs.com/settings/dorokuma/profile`）+ `npm publish` 自身的 PUT 兜底"处理（决策 2）。

## 被放弃的方案（必填）

- **直接用 `npm profile get` 的退出码当门禁、失败即中止**：自动化 token 下必然 E403，会把能成功的发布误判为无权限。放弃，改为"whoami + E404 + gh auth status + tarball 打包/隔离安装"的可执行组合，并把邮箱/2FA 的人工确认写成明文步骤。
- **换一条别的 npm 命令读取账号资料（例如 `npm token list`）来替代 `npm profile get`**：实测该命令可用（`exit 0`，含 `bypass_2fa` 与 `permissions[...].write`），但发布门禁不该依赖"读账号资料"这类权限，而且它会把 token 元数据（标识、权限、到期时间）写进发布日志，与"凭据不扩散"相抵。放弃，改用不依赖账号资料读权限的证据组合，账号姿态另按"人工一次性账号检查 + publish PUT 兜底"处理。
- **把 CHANGELOG 状态行统一写成"已发布"**：在"提交已推、产物未发"的窗口里与 registry 不符，且失败中止/换版本要多补一次纠正提交。放弃，改为"默认不写状态行"，或只写"写提交时已成立"的事实。
- **先打 tag、后 push 发布提交**：tag 会永久封进"README 仍指向旧 tag"的快照（tag 不可移动）。放弃，改为 push + `HEAD` = `origin/main` 校验通过后再建 tag，并补快照校验命令。
- **由 agent 自行拍定部分发布时的版本档位**：档位决定 caret 使用者的升级行为（同 0.13.0 的 minor 抉择），属用户决策。放弃，只把 `calculated default`（按最后一个完整发布计算）与判据写进文档。
- **本轮顺手把 CHANGELOG 0.13.2 段的"已发布"改成事实口径**：会改动 CHANGELOG（本轮明确禁止）且属对已发布版本的追溯改写。放弃，新口径只对**后续**版本生效，本次写法作为偏差记录留痕。
