# 0.13.3 发布落地事实

## 一句话结论

0.13.3 作为**同一发布单元**落到了 npm（`@dorokuma/herdsman@0.13.3` + `@dorokuma/herdsman-pi@0.13.3`，两包 `dist-tags.latest` 均由 `0.13.2` 前进到 `0.13.3`）与 git（tag `v0.13.3` peel = `af9ea12` = 发布提交 = `origin/main`），GitHub Release 已建；本次走 **ff-only**，tag 直接指向发布提交本身。发布过程**无失败步骤**：两次 `npm publish` 均 exit 0、无 republish、无回滚、无人工修复；唯一需要留痕的口径问题是 `## Preconditions` 的 `HEAD = origin/main` 一条在 push 之前按构造不成立（见下）。**发布当时未部署生产**（下一步，等用户点头；此后该版本已按 registry 渠道部署到生产，见「证据落点与清理状态」）。

## Preconditions 的 `HEAD = origin/main` 口径解释（**必须留痕**）

`docs/releasing.md` 的 `## Preconditions` 含 `test "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)"`。该段是设计成**发布起点**（发布提交存在之前）跑的；本次流程把它挪到发布提交 `af9ea12` 之后、`git push origin main` 之前，因此这条**按构造必然为假**（发布提交当时只存在于本地，`origin/main` 仍是 `482ada0`）。实测 `exit=1`。

裁定（主代理已复核并放行）：该行由 push 后检查满足，不作为停手条件。**这不是「这条门禁可以跳过」**：`## Preconditions` 的设计时点是**发布起点**（发布提交存在之前），该行在那一点成立；唯一会让它按构造为假的动作是「在发布提交之后整块重跑 `## Preconditions`」，其判据由 push 后的同名检查复验（下条 3）。依据三条：

1. **起始态证据已满足该检查的目的**：「从陈旧/脏的 main 发版」已排除 —— 出发点是 `main` = `origin/main` = `482ada0`、工作树干净、纯 `--ff-only` 合入（无合并提交）、发布提交 `git diff HEAD^ HEAD | sha256sum` = `09271ce9…` 与审过的字节逐字相同。
2. **文档自己把同名检查放在 push 之后**：`## Commit and create a local tag` 的顺序是 commit → `test -z "$(git status --porcelain)"` → `git push origin main` → `test "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)"`。
3. push 之后该检查实测 `exit=0`（`HEAD` = `origin/main` = `af9ea12`，且 `git ls-remote origin refs/heads/main` 逐字相符）。

release 那一刻各项门禁均绿：分支 `main`、工作树空、`npm whoami` = `dorokuma`、`gh auth status` 通过、两条 `npm view` 均为 E404。
